## Docker and the database seam

[next.config.ts](next.config.ts) sets `output: "standalone"`; the [Dockerfile](Dockerfile) is a three-stage build (deps → builder → runner) that ends up running `node server.js` as a non-root user. Two constraints follow from that and will bite when the project grows:

- `public/` and `.next/static/` are **not** part of the standalone bundle — the runner stage copies them explicitly, so a new top-level static directory needs its own `COPY`.
- The builder stage needs devDependencies, because `next build` shells out to the local `tsc`.

[docker-compose.yml](docker-compose.yml) runs the app next to a `db` service. **PostgreSQL is reserved but not wired**: the app service already receives `DATABASE_URL` (host `db`, published on 5432 for host-side `npm run dev`), and no code reads it yet. [.env.example](.env.example) is the template for `.env`, which is gitignored and used by compose for interpolation. Note that `NEXT_PUBLIC_*` and `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` are **build** arguments, not runtime environment — both are frozen into the build output.

## Next.js 16 conventions that differ from older Next.js

These fail silently or at build time if you write them the old way:

| Old habit | In 16.3.5 |
|---|---|
| `middleware.ts` / `export function middleware` | `proxy.ts` / `export function proxy` — Node.js runtime only; setting `runtime` in the file throws |
| `params.slug`, `searchParams.q` | `await params`, `await searchParams` — sync access is fully removed, no compat layer |
| `const c = cookies()` | `await cookies()` (also `headers()`, `draftMode()`) |
| `revalidateTag('posts')` | `revalidateTag('posts', 'max')` — one-arg form is a TypeScript error |
| `error.js` with `reset` | `retry` — re-fetches and re-renders; `reset` only clears error state |
| `unstable_cacheLife` / `unstable_cacheTag` | `cacheLife` / `cacheTag` |
| `Image` `priority` | deprecated → `preload`; `qualities` is now required config; `images.domains` → `remotePatterns` |
| `next.config.cjs` / `.cts` | unsupported — `.ts` / `.mts` / `.js` / `.mjs` only |
| custom `webpack` config | makes `next build` fail outright; `--webpack` is the opt-out, `--turbopack` is a no-op |
| parallel-route `@slot` without `default.js` | build failure — every slot needs one |

Removed entirely: AMP, `next lint`, `serverRuntimeConfig`/`publicRuntimeConfig`, `swcMinify`, `target`, `NextRequest.ip`/`.geo`, `experimental.ppr`/`dynamicIO`/`useCache`.

For anything not listed here, read the matching guide in `node_modules/next/dist/docs/` before writing code — it is the version-exact documentation for 16.3.5. `01-app/04-glossary.md` is the fastest way to load the v16 vocabulary, and `01-app/02-guides/upgrading/version-16.md` is the full breaking-change list.

## Caching model — the one open architectural decision

[next.config.ts](next.config.ts) is empty, so `cacheComponents` is **off** and the project runs the route-level model (`dynamic` / `revalidate` / `fetchCache` segment exports), close to Next 15 behavior. Enabling it is a top-level flag (`cacheComponents: true`, not under `experimental`) that replaces `ppr` + `useCache` + `dynamicIO` with one switch, and changes the ground rules:

- PPR becomes the default (`◐` static shell + streamed dynamic content), `"use cache"` becomes the opt-in cache primitive, and `fetch` stays uncached by default either way.
- `dynamic` / `revalidate` / `fetchCache` / `dynamicParams` segment exports start **erroring**, and Node.js becomes the only runtime.
- Client navigation preserves component state via React `<Activity>` instead of unmounting — dropdowns, dialogs, form drafts, `<video>` playback, and global styles all leak across navigations unless explicitly reset. Logging out must use `window.location.href`.
- Uncached data or runtime APIs during prerender become **build errors**, fixable with `<Suspense>`, `"use cache"`, or `export const instant = false` (a blocking escape hatch with no fallback UI).

Two constraints hold in both models: cache entries are keyed by build ID, so they never survive a deployment, and cache keys/tags are stored in plaintext — never put tokens, passwords, or raw emails in a `"use cache"` parameter or `cacheTag`.

## Security rules specific to this stack

- **Server Actions need their own authorization.** A page-level `auth()` check controls which UI renders, nothing more — an action defined in that page is a separately reachable POST endpoint. Re-verify the session and check ownership inside every action; schema validation only checks shape, not that the caller owns the row.
- **Keep `process.env` and DB access inside a Data Access Layer** (`import 'server-only'`) once one exists; upstream recommends picking one data-fetching approach and not mixing the three.
- **Proxy matchers are not a security boundary for actions** — Server Functions POST to the route that uses them, so a path excluded from the matcher also skips proxy checks for its actions. Keep proxy checks optimistic (cookie reads only; it runs on every route, including prefetches).
- Don't authenticate by `return null` in a layout, and don't write cookies or invalidate caches during render — those belong in Server Actions.
