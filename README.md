# Weact小本本

> **we activity** — 和朋友一起策划、记录、回顾每一场活动。

Weact小本本 是一款活动管理应用。你把朋友拉进一个小团体，定下聚餐、玩耍、旅行
或你自己添加的类型的初步计划，大家投票拍板；活动过程中和结束后可以发文字、图片、
语音感想，打分、分账；需要出行的活动还能查交通住宿。
时间长了，它会替你生成年度回顾和好友亲密度。

## 功能点

### 1. 账号与登录
- **手机号登录**，登录时校验手机号格式（11 位，`1[3-9]` 开头，自动去掉空格、短横线和 `+86` 前缀）。
- 未注册的手机号**自动注册**，注册后跳转设置密码。
- 密码规则：**至少 8 位，且至少包含一个小写字母和一个数字**。表单实时列出未满足的规则。

### 2. 好友与关系标注
- 通过手机号**发送好友请求，需要对方同意**才成为好友 —— 不是加上就成立。
- **不做实时推送**：对方下次打开好友页时才看到请求。好友菜单右侧有未读条数徽标，
  同样是在下一次页面加载时更新。
- 请求方在等待期间能看到自己发出的请求，并可以**撤回**；被请求方可以**同意**或**拒绝**。
  拒绝不通知请求方（被拒绝与否，请求方从自己那条等待记录消失就能看出来）。
- 同意之后**双方**都会收到通知（「你和 X 已成为好友」），而**刚加上的好友卡右上角带
  `new` 标记**。通知和标记都在看过之后消失 —— 离开好友页再回来就不再显示。
- 双方互相发送请求时**直接成为好友**，不需要谁去点同意。
- **删除好友是单边的，效果是双边的**：好友卡上的「删除」弹确认框，确认后两个人互相从
  对方的列表里消失。对方**不会**收到通知（被删除与否，对方从自己列表里少了个人就能
  看出来）—— 和「拒绝不通知请求方」是同一个结构，不是漏做了一步。
- 可给好友标注关系：朋友 / 好友 / 恋人 / 家人 / 同事 / 同学 / 其他。
- **关系可以随时修改，且只有自己可见** —— 同一条好友关系，双方看到的关系互不影响
  （所以关系存在「关系 × 拥有者」上，不存在好友关系边上）。对方向你发来的请求卡片上
  也**不会**显示对方给你标的关系。

### 3. 活动列表与详情
- 登录后进入历史活动列表，**只展示关键字段**：类型、主题、时间、地点、人均、成员头像。
- 点击任意活动进入详情页，按分区展示全部内容：概览 / 计划·投票 / 评论·感想 /
  打分·分账 / 交通·住宿（旅行类，以及勾选了「需要交通住宿」的自定义类型）。

### 4. 新建活动
- 活动类型：内置的**聚餐 / 玩耍 / 旅行**，加上**用户自己添加的类型**（见第 9 节）。
- 表单顺序：主题 → 时间（起止）→ 地点定位 → **拉人** → 预计花费 / 预计人均 → 具体说明。
  拉人排在预算之前，是因为人均是按人数摊出来的 —— 先定人，再看人均才讲得通。
- 起止时间用**自研的主题化日期时间选择器**（日历 + 时/分），不是原生
  `<input type="datetime-local">` —— 原生控件的弹出日历走系统样式，圆角、配色都和主题对不上。
- **拉人进小团体有两条路**：
  - 好友快捷列表（来自「我的好友」）点一下选中；
  - **对方还不是好友时，直接输手机号拉进来** —— 这类成员标记为「待接受」，
    在数据库里是 pending invite，等对方注册/接受后才落到 `activity_members`。
- 填了总预算后按当前人数自动估算人均（好友 + 待接受邀请 + 你自己）。
- 之后可以在活动内**提出多个方案 → 投票 → 拍板最终计划**。

### 5. 活动进行中与结束后
- **评论感想**：支持文字、图片、语音三种形式，活动过程中和结束后都能发。
- **打分**：活动结束后可对本次体验打 1–5 星。
- **分账**：记录总额、每人应付与实际已付，算出谁该给谁转多少。
- **旅行实时信息**：需要出行的活动可查交通（航班/车次）与住宿，并标注报价的新鲜度。

### 6. 回顾与亲密度
- 按年（或季度）生成活动回顾：活动总数、分类占比、年度之最等。
- **亲密度统计**：根据共同活动次数、互动频率和最近一次见面的时间衰减，
  算出和每位好友的亲密度（0–100），用柱状图展示。

### 7. 分享
- 活动可以生成长链接分享给未注册的人，落地页只暴露分享者选择公开的内容。
- **关于微信分享**：微信自定义分享卡片需要 JS-SDK，而 JS-SDK 要求已认证的公众号、
  已备案并绑定该公众号的域名，以及服务端签名接口 —— 对自部署应用来说成本过高，
  短期内不做。目前采用**系统分享面板（`navigator.share`）+ 复制链接**：
  在 iOS/Android 上系统面板本身就会列出微信，微信内置浏览器里也能用右上角「…」正常转发，
  覆盖面和 JS-SDK 基本一致。

### 8. 主题与外观
- 三个内置主题，都是完整配色而非简单换色：
  - **温馨**（默认）：奶油底 + 珊瑚/陶土主色，大圆角。暖色浅调。
  - **冷酷**：深空蓝黑底 + 电光青主色，更锐利的圆角。冷色深调。
  - **商务**：白底 + 中性灰阶 + 一个克制的冷色（深钢蓝 `#1a52a1`），最小的圆角。
    黑白灰为主，**没有辉光**。
- **主题不等于明暗。** 温馨和商务都是浅色，冷酷是唯一的深色 —— 所以没有
  「商务 + 深色」这类组合，也不跟随系统设置，首次访问一定是温馨。
- 选择存在本机（`localStorage`），页面加载时由一段阻塞式内联脚本在**首次绘制前**写入，
  不会出现先闪一下默认主题的情况。
- 背景顶部有一层低透明度的主色辉光（每主题一套 `--ambient` 径向渐变，
  商务主题显式写成 `none`）。
- 全站适配 PC 与移动端：`md` 以上是固定侧边栏，以下是顶部栏 + 底部 Tab。
- **已知不协调**：活动类型徽章和结算页星标是写死的彩色 Tailwind 字面量
  （见 [§9](#9-自定义活动类型)），在商务主题下会保持彩色。它们依然清晰可读，
  只是配色不搭 —— 要真正灰化需要让色板按主题分叉，是独立的一次改动。

### 9. 自定义活动类型
- **内置三种是固定的**：聚餐 / 玩耍 / 旅行不能改名、不能删除、不能换色。
  这是产品决定，不是没做完 —— 它们在任何主题、任何设备上都必须长得一样。
- **自定义类型可以新建、改名、删除**，颜色**自动分配**（用户不选色）。
  两个入口：设置页的「活动类型」卡片，以及新建活动表单里的「新建类型」
  （在表单里建完会**自动选中**，不用回头再点一次）。
- 每个自定义类型可以勾选**「需要交通住宿」**，勾了之后用它的活动详情页会多出
  「交通 · 住宿」分区。
- 类型名称上限 12 字，且不允许与内置或已有自定义类型重名。
- 类型保存在本机 `localStorage`，换设备/换浏览器就没了。

#### 两个决定了实现的约束

**Tailwind v4 不能在运行时拼类名。** 自动分配的颜色必须是在源码里写死的
**完整字面量**（`ACTIVITY_TYPE_ACCENT_PALETTE` 里 8 组），按 `paletteIndex` 取。
`bg-${hue}-500/10` 这种拼出来的类名 Tailwind 扫不到、不会生成、**静默失效** ——
徽章会变成没有底色的裸文字，而且不报任何错。色板色相刻意避开内置的
amber/violet/sky，每色都带 `dark:` 变体（全站 `dark:` 被重映射到冷酷主题，
所以一套类名同时适配三套主题：冷酷走 `-400` 那支，温馨和商务走 `-700` 那支）。
实测三套主题下 8 色 + 3 个内置的对比度都 ≥ 4.5:1（WCAG AA 正文标准），
**最紧的是浅色主题下的橙色 4.66:1** —— 商务主题的卡片是纯白（比温馨的奶油底更亮），
对比度只会更高，不会更低。再加颜色时用同样的 `-500/10` 底 + `-700` 前景组合，
并复核这个数。

**放宽类型后编译器不再报警。** `ActivityType` 从三字面量联合放宽成 `string`，
而 `tsconfig.json` 没开 `noUncheckedIndexedAccess`，所以 `TABLE[type]` 在 key
不存在时类型仍然成立、运行时静默是 `undefined` —— 原本四处直接下标取值会
**不报错地渲染出空徽章和 `undefined 次`**。因此所有取值都收敛到
`resolveActivityType()` 一个函数，解析不到时降级成「未知类型」中性徽章，
而不是崩溃或留空。旧的 `ACTIVITY_TYPE_LABEL` / `ACTIVITY_TYPE_ACCENT` 两个导出
已删除 —— 留着它们就等于留着无兜底的取值入口。

#### 已知取舍

- **自定义类型只存在本机。** 没有后端，所以别人打开你分享的活动链接看到的会是
  「未知类型」。接后端时这张表挪到服务端即可，`resolveActivityType()` 不用动。
- **删除类型不会删除用了它的活动**，那些活动的徽章会降级成「未知类型」，
  并失去交通住宿分区。删除确认框里写明了这一点。
- **颜色不复用**：新类型的 `paletteIndex` 取「已有最大值 + 1」而不是数组长度 ——
  按长度算的话，删掉一个类型后下一个就会拿到一个仍在使用的颜色。
- **跨标签页同步**靠 `storage` 事件（在一个标签页删除类型，另一个已打开的页面
  会自己更新，不用刷新）。
- 年度回顾的分类统计跟着走，但数据本身仍是静态 fixture。

### 主题是怎么实现的

主题状态挂在 `<html>` 的 `data-theme` 属性上（`warm` / `cool` / `business`），
`globals.css` 里三套 CSS 变量块分别覆盖。关键的一步是**把 `dark:` 变体重映射到冷酷主题**：

```css
@custom-variant dark (&:is([data-theme="cool"] *));
```

shadcn 生成的组件内部有 61 处 `dark:` 工具类（如 button 的 `dark:bg-input/30`），
重映射后它们在冷酷主题下自动生效，**一个组件都不用改写**。这里的 `dark` 指的是
主题身份，不是「用户偏好深色」—— 项目里没有 `prefers-color-scheme` 驱动的样式。

注意这条重映射**只认冷酷**。温馨和商务都是浅色，刻意不拿那些 `dark:` 覆盖 ——
那些规则全是「在近黑底上还能看」的补偿，浅色主题要它们反而是错的。所以加商务主题时
这个变体一行都没改。

主题的读取不经过 React state，而是 `useSyncExternalStore` 直接读 DOM 属性
（`lib/theme.ts` + `hooks/use-theme.ts`）—— 因为内联脚本在 hydration 之前就已经改过
那个属性了，以 DOM 为准才不会打架，也就不需要 Provider 或 `mounted` 标志。

#### 加第四个主题要改哪里

`lib/theme.ts` 是**唯一的事实来源**：`THEMES` 数组、由它派生的 `Theme` 联合类型、
`isTheme()`、以及那段防闪烁内联脚本全部从它推导。加一个主题需要动的地方是：

1. `lib/theme.ts` 的 `THEMES` 加一项 —— 同步补 `CHROME_COLOR`（`Record<Theme, …>`，
   漏了会编译报错）
2. `app/globals.css` 加一个 `[data-theme="…"]` 变量块，**记得写 `--ambient`**
   （不写会继承 `:root` 的橙色辉光）
3. `components/theme-toggle.tsx` 的 `THEME_META` 加一项（同样是 `Record<Theme, …>`，
   漏了会编译报错）

> 这两处 `Record` 是刻意的。它们原先是一个 `as const satisfies ReadonlyArray<…>`，
> 但 `satisfies` **只校验列出来的项合法，不校验每一项都列了** —— 加了主题却忘了加选项
> 会静默通过编译，新主题永远不可达。`Record` 才会真的报错。

> 三处 `--background` 相关值必须一致：`lib/theme.ts` 的 `CHROME_COLOR`、
> `app/layout.tsx` 的 `themeColor`（已经从 `CHROME_COLOR` 派生，不用手动同步）、
> 以及 CSS 变量块的 `--background`，否则移动端浏览器地址栏颜色会对不上。

### ⚠️ `components/ui/` 里有两处本地补丁

两个都是**生成物漏掉了高度约束**这一类缺陷，修在 primitive 层比在每个调用点各打一遍补丁更合适。
改动处都有 `LOCAL PATCH` 注释。

**`dialog.tsx` — `DialogContent`**

原本只约束宽度不约束高度，而遮罩层是不可滚动的 `fixed inset-0`，
所以任何高于视口的对话框上下两端都会被裁掉且无法触达（横屏手机、软键盘弹起时必现）。
补丁加了 `max-h-[calc(100dvh-2rem)] overflow-y-auto`。

**`popover.tsx` — `PopoverContent`**

同一个预设里的其他弹出层（`select.tsx`、`dropdown-menu.tsx`）都已经带了
`max-h-(--available-height) overflow-y-auto`，只有 `popover.tsx` 漏了，
于是高于可用空间的 popover 会直接溢出视口且无法滚动。
`--available-height` 是 Base UI 在 positioner 上算好的可用高度，会继承下来。

> 这个补丁是加日期时间选择器时暴露出来的：加上「确认」按钮后弹层高 403px，
> 在 390×500、844×390（横屏）这类视口下会溢出屏幕。修复后短视口内部滚动、
> 正常视口（桌面 1280×900、手机 390×844）行为完全不变。

**重新执行 `shadcn add dialog --overwrite` / `shadcn add popover --overwrite`
会分别覆盖掉这两个补丁。**

## 开发

```bash
npm run dev                 # next dev（Turbopack），产物在 .next/dev
npm run build               # next build（不再运行 lint）
npm run lint                # eslint
npx next typegen            # 重新生成路由类型（tsc 需要它）
npx tsc --noEmit            # 类型检查
```

Docker：

```bash
docker compose up --build   # db → migrate → app
```

三个服务，启动顺序由 compose 保证：

| 服务 | 作用 |
|---|---|
| `db` | PostgreSQL 18。应用和迁移都连它。 |
| `migrate` | 跑一次 `./drizzle` 里所有未应用的迁移，然后退出。与 app 同镜像不同阶段（`target: migrator`）。 |
| `app` | Next.js standalone。**等 `migrate` 成功退出才启动**。 |

`migrate` 与 `app` 必须分开，因为 `app` 那个镜像里根本没有迁移文件和 `drizzle-kit`：
`next build` 只会把**服务端运行时真正 import 的东西**打进 standalone 产物，而没有哪一行运行时代码会去读
`./drizzle`。反过来说，`migrate` 阶段依赖 `deps` 阶段装了 devDependencies（`drizzle-kit` 在那里）——
给 `npm ci` 加上 `--omit=dev` 会让它在部署那天才炸。

迁移失败时应用**不会**启动，而不是带着一个没建好的 schema 硬起 —— 这是有意的方向。

管理员变量要给 `.env`，不是 `.env.local`：compose 的插值只读 `.env`，而 `.env.local` 只有 Next 自己加载。

### 接入后端时的注意事项

- 所有 `TODO` 注释标记了需要接 Server Action 的位置。
- **每个 Server Action 都必须独立鉴权**：页面级的会话检查只决定渲染什么，
  Action 本身是一个独立可达的 POST 端点，必须重新校验会话和行归属。
- **分享 token 必须不可枚举**：绝不能用活动 id 当 token，否则整个 id 空间可被遍历。
  分享页已经设了 `noindex`。
- **好友关系必须按 `ownerId` 过滤**：`friendships` 是全局表，一条记录不代表「我的好友」。
  已落地的读法是 `lib/friends/dal.ts` 的 `listFriends(session.userId)`，好友页和活动
  成员选择器都走它。漏掉这个过滤会把**别人的私密关系标注**渲染出来 ——
  关系标注只对拥有者可见，这是硬要求。同一个理由让「别人发来的好友请求」投影里
  根本没有 `relation` 这个字段：那一行的标注是**发起方**给接收方标的。
- **`friendships` 还有一层状态**：一条行只有 `status = 'accepted'` 才算好友，
  `pending` 是待同意的请求。任何新的读法都要带上这个条件，否则会把没同意的请求
  当成好友；任何新的写「同意/撤回/拒绝」的路径都要带 `status = 'pending'`，
  否则会静默解除一段已成立的好友关系。
- **一段好友关系是两行，删除必须删两行、且必须在一个事务里**：表是有向的，
  `(我→Ta)` 和 `(Ta→我)` 各一行。`lib/friends/dal.ts` 的 `deleteFriendship` 先删
  自己那条 `accepted` 边（**这一步就是授权**：删不到就返回 false，一行都不动），
  再删反向那条。中间那个状态是「单向好友关系」，只有对方能修，所以两条语句必须
  整体成功或整体不发生。**不要把它合并成一条带 `OR` 的 DELETE** —— 守卫失败时
  第二段照样会执行，等于把「Ta 发给我的待处理请求」也删了，一次不需要授权的写。
- **手机号要防枚举**：按手机号拉人的接口不能回显「该号码是否已注册」，
  否则可以拿来批量探测账号。加好友那条路：四种结果共用同一条回执文案，其中
  「没注册」「注册了没取名」「被限流」三种的**整个 HTTP 响应逐字节相同**（实测 108
  字节，连打 25 次跨过限流线后 26 个响应完全一致）。「本来就是好友」响应更大
  （15521 字节）—— 它走的是自愈路径，`revalidatePath` 把重渲染的页面装了进去。
  那不泄漏新信息：调用者本来就能在自己好友列表里看到这个人。
  **而请求制本身削弱了这条保证** —— 加一个已注册的号码会在「等待对方同意」里留下
  一条记录，加未注册的不会。这是已知代价（见 `lib/friends/actions.ts` 里 `NOTICE`
  上那段注释），不是疏漏。
  活动侧的「手机号拉人」还停在只校验格式、不查注册状态。
  服务端还需要限流，并且不能仅凭前端传的 id 就写入 `activity_members`。
- **自定义活动类型挪到服务端时**：类型名称是用户输入、且会出现在别人能打开的分享页上，
  12 字上限和重名校验目前只是客户端提示（`isLabelTaken` 只防误操作，不防攻击），
  必须在服务端重新强制。类型 id 也要校验归属 —— 否则一个构造出来的 `type` 值
  可以让活动引用别人账号下的类型。读取端仍然全部经过 `resolveActivityType()`，
  所以**解析逻辑不用改**，只是解析数据源从 localStorage 换成服务端查询。
- **改密码必须在同一个事务里「换哈希」+「作废其他会话」**，`lib/auth/dal.ts` 的
  `changePassword` 就是这么写的。只做一半的两个中间态都是「用户相信了一件不成立
  的事」，而且**都不会自愈**：只换哈希不删会话，偷到 cookie 的人还在里面，而用户
  没有任何理由再点一次「修改密码」；只删会话不换哈希，旧密码还能登。当前设备那一行
  靠 `token_hash <> keep` 留下来 —— 它由调用方从会话 cookie 算出（
  `currentSessionTokenHash()`），DAL 永远不碰 cookie。**将来若实现「早于
  `passwordSetAt` 的会话视为陈旧」那条规则，必须把这条故意留下的会话排除掉**，
  否则会把用户手上这台也踢下线。
  写库那一步用 `WHERE id = $1 AND password_hash = $2` 做 CAS：两台设备同时改密时
  后者匹配不到行、返回 false，而不是静默覆盖前者。
- **两个限流桶必须保持独立**（`lib/rate-limit.ts`：加好友 20 次/小时、改密码
  5 次/小时，各自一个 `Map`）。合成一个计数的话，一个已登录的人拿一批号码去试就能把额度
  刷满，然后**同一个账号连自己的密码都改不了**；反过来在改密码上试错几次也会连带
  加不了好友。让一个功能给另一个当拒绝服务的道具。被限流时**要不要如实回话取决于
  这个端点泄不泄漏信息**：加好友必须用和成功逐字节相同的响应，改密码可以直说
  （调用者本来就是账号本人）。
- **界面改动必须过移动端那一关**：320×844 和 390×844 两个宽度下，页面不能横向滚动，
  每个可点目标的**有效高度 ≥ 44px**（视觉尺寸可以更小，用 `after:absolute
  after:-inset-y-*` 的伪元素把命中区撑起来 —— 见 `components/theme-toggle.tsx`），
  不能有元素被 `overflow: hidden` 祖先裁掉。全局触控地板落在几个基元上
  （`components/ui/button.tsx` 的全部尺寸档、`input.tsx`、还有 `date-time-picker.tsx`
  那个写死的 `h-11`），**要加新的高度类之前先看基元里有没有**。
  **横向一律不扩命中区**：相邻控件之间常常只有 2–8px，横向一扩两块命中区就重叠，
  点在左边那颗的右半边会触发右边那颗。宽度的下限是 WCAG 2.5.8 的 24px，不是 44px。
- 环境变量与数据库访问应集中在一个 Data Access Layer（`import 'server-only'`）。
- 缓存模型尚未决定：`next.config.ts` 里没有开 `cacheComponents`，
  当前是路由级缓存模型。开启它会改变全局渲染规则，是个单独的决定。
